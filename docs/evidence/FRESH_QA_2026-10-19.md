## Confirmed findings

### P1 — incomplete unified replacements become successful insertions or deletions

`harness/lib/hashline-core.ts:210-248` discards both declared hunk counts and
chooses the operation from whichever prefixed rows remain. Against `old\nkeep\n`,
an exact-tagged `@@ -1,1 +1,1 @@` followed only by `+new` succeeds as an insertion,
producing `old\nnew\nkeep\n`. The absent old side is never checked. The opposite
missing side can be treated as a deletion. An exact file digest proves the source
version, not that this incomplete edit expresses a safe interpretation of intent.

Repair: reject missing required sides; restrict any stale-count compatibility to
cases with an explicit, fully validated transformation. Keep legitimate zero-count
insertions/deletions distinct. Test truncated bodies through the complete write path.

### P2 — a context row can escape source validation

At `harness/lib/hashline-core.ts:217`, `row.trim()` turns the legitimate context
row ` *** End Patch` into a control delimiter. A hunk containing this context row
succeeds even when the corresponding source line says `DOES NOT MATCH`. The
claimed guarantee that every old/context line is checked is therefore false.

Repair: classify diff prefixes before wrappers. Only an unprefixed wrapper may end
a patch; context rows must always remain data and undergo exact source checking.

### P2 — unchanged context bytes are rewritten

The converter at `harness/lib/hashline-core.ts:239-241` treats the complete hunk,
including context, as one replacement. `applyHunks` then assigns the range's
dominant line ending to those context rows. A one-line change in
`prefix\nold\r\nsuffix\r\n` produces `prefix\r\nnew\r\nsuffix\r\n`, modifying
the unchanged prefix's LF terminator. This differs from a native tight replacement.

Repair: preserve context rows as original document lines and apply only actual
change runs, while still validating the whole declared source span. Cover mixed
line endings, BOMs, and final-newline state.

### P2 — valid screen crops are rejected after capture

`createMacScreenCapture` already crops the image and returns the cropped dimensions
plus its original viewport (`harness/lib/visual-capture.ts:113-120`). The tool then
checks the original crop against those smaller dimensions at
`harness/extensions/visual-observe.ts:256`. For example, a valid original crop at
`x=10,y=10,width=2,height=1` is refused against the returned `2x1` image.

Repair: validate bounds in the original coordinate space once, then validate the
adapter's returned crop geometry without applying the original offset a second time.
This affects `visual_observe`; it is separate from the new plain `screenshot` tool.

## Lower-priority compatibility limitation

`parsePatch` switches the entire input to unified syntax when any `@@` marker
exists. One native section followed by a tagged-unified section is rejected. It
fails safely, but is another possible retry source. Either support per-section
syntax or explicitly disclose the all-one-format restriction.
